# Составы, выбранные турниры и Jupyter

## Выбор турниров

В `config/tournament_families.json` выбраны основные серии:
BLAST Slam, ESL One, DreamLeague Season, Esports World Cup, PGL Wallachia и The International.
Последний добавлен по строке Valve на предоставленном календаре. Квалификации и
DreamLeague Division 2 исключены. FISSURE пока не включён целиком: уровень нужно проверять
для конкретного события. Можно добавить подтверждённые события через `LEAGUE_IDS`.

Сборщик сопоставляет названия `/leagues` с семействами. Это **пользовательская выборка**,
а не автоматически подтверждённая классификация Liquipedia. `TOURNAMENT_SCOPE=selected`
включён по умолчанию; `TOURNAMENT_SCOPE=all` возвращает прежний сбор всех pro-турниров.
Непустой `LEAGUE_IDS` имеет приоритет. Пустой результат сопоставления не отключает фильтр.
Имена OpenDota могут отличаться — проверяй покрытие и используй точные ID при необходимости.

## Команды и игроки отдельно

`raw.team_profiles` и `raw.player_profiles` хранят ответы API отдельно. DAG обновляет до
`PROFILE_LIMIT` профилей каждого типа за запуск (по умолчанию 20), повторно не чаще раза
в 7 дней. Недоступные профили отмечаются в результате задачи как deferred и не мешают
строить матчевые витрины. Отображаемое имя может быть взято из карты, если профиль отсутствует.
Карьерные агрегаты текущего профиля не используются при оценке исторической модели.

`stg_player_matches`/`fct_player_matches` хранят участие и показатели игроков в каждой карте.
`fct_team_rosters` определяет пятёрку по пяти различным известным Steam32 ID.
`roster_spells` — последовательные периоды одной пятёрки; `current_rosters` — последняя
**наблюдаемая** пятёрка и её статистика. `dim_teams`/`dim_players` — отдельные профили.

Смена A → B → A считается тремя периодами. Замена одного игрока начинает новый период.
Это включает стендинов. Дата первого появления — нижняя граница наблюдений, не официальная
дата трансфера. Пропуски матчей могут скрыть изменения, а неизвестные ID исключают карту
из анализа состава. Последняя известная пятёрка не гарантирует состав будущей карты.

## Запуск Jupyter в Windows

Из корня локального клона:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-analysis.txt
.\.venv\Scripts\python.exe -m jupyterlab
```

Если `.venv` ещё нет, сначала `python -m venv .venv`.
Открой:

- `notebooks/01_team_player_roster_overview.ipynb` — покрытие, профили, последние составы,
  форма команд, пики/баны текущих пятёрок и история игроков.
- `notebooks/02_roster_forecast.ipynb` — признаки, хронологический holdout,
  сравнение Elo/50%/логистической регрессии и функция условного будущего прогноза.

По умолчанию обзор начинается **с 1 января 2026**, исторические признаки — с 2023 года.
Ноутбуки не скачивают данные скрытно. Без файла `data/analysis.json` запускается явно
отмеченное синтетическое демо, на котором модель **не обучается**.

### Реальные данные без PostgreSQL

Небольшая ограниченная выборка последних профессиональных матчей выбранных семейств:

```powershell
.\.venv\Scripts\python.exe -m dota_scout.cli snapshot --pages 10 --limit 60 --profile-limit 10
```

Нужен сетевой доступ. 60 — максимум запросов деталей, а не обещание 60 подходящих карт.
Сборщик ограничивает частоту до одного запроса примерно в секунду, но ответы API могут
идти значительно дольше. По умолчанию общий лимит времени 300 секунд (`--max-seconds`),
промежуточные карты сохраняются после каждого ответа. Snapshot хранится
локально в `data/analysis.json`, не коммитится и не является полной историей.

### Экспорт накопленных данных из Docker

```powershell
docker compose exec airflow python -m dota_scout.cli profiles --limit 20
docker compose exec airflow python -m dota_scout.cli export --output /opt/project/data/analysis.json
New-Item -ItemType Directory -Path data -Force
docker compose cp airflow:/opt/project/data/analysis.json ./data/analysis.json
```

Многолетнюю историю загружай существующим `sync --pages ... --before ...`, проходя
курсор назад. Не требуется полная история команды под всеми прежними составами:
важнее покрытие текущей пятёрки и история каждого игрока. Первые наблюдения в короткой
выборке не доказывают, что состав только что сформировался.

Переменные для другого периода/набора перед запуском Jupyter:

```powershell
$env:SCOUT_ANALYSIS_START = '2026-01-01'
$env:SCOUT_HISTORY_START = '2023-01-01'
$env:SCOUT_DATA_PATH = 'D:\Github\dota2proleague\data\analysis.json'
```

## Как устроен прогноз

Для каждой карты используется известная для этого сценария пятёрка. Рейтинги и форма
обновляются только результатами карт, уже завершённых до начала предсказываемой карты.
Новый состав сбрасывает командный Elo и форму, но переносит историю игроков.
Игрок с неизвестной историей получает нейтральный рейтинг 1500.

Признаки: разница Elo пятёрок, среднего Elo игроков, сглаженной формы последних 20 карт,
числа совместных игр и опыта игроков. На выходе вероятность победы Radiant/Dire в карте.
Стороны и составы для будущего прогноза задаются явно. Нет предсказания серии bo3/bo5.

Тест — последние 25% времени. Обучающие карты, не завершённые к границе, исключаются.
Скалирование обучается только на train. Тестовые результаты могут обновить Elo для
более поздних тестовых карт после завершения, но не коэффициенты модели.
Оценка — log loss, Brier score, accuracy и график калибровки; сравнение с 50% и Elo.

Минимум 80 пригодных реальных карт — технический порог MVP, не доказательство качества.
Отдельный временной набор для настройки/калибровки пока не реализован, поэтому
гиперпараметры фиксированы. Роли, баланс патчей и официальные трансферы не учитываются.
Обучение на синтетическом демо или выдача выдуманной точности не производится.

## Проверки

`tests/test_forecast.py` проверяет отсутствие будущих исходов в признаках, пересекающиеся
по времени карты, сброс истории нового/вернувшегося состава, сохранение истории игроков,
хронологическое разделение и исключение квалификаций/низших дивизионов.
Интеграционный тест PostgreSQL проверяет смену пятёрки и отдельную историю игрока.
`scripts/check_notebooks.py` выполняет оба ноутбука на помеченном демо и сохраняет
результаты только в игнорируемой папке `data/notebook_checks`.
